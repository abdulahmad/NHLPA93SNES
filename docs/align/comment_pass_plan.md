# Comment pass plan: bring 93G comments to 93S

Generated by /tmp/claude-0/s/measure.py + post.py (read-only measurement; no repo file changed). Plan: /tmp/claude-0/s/comment_plan.json (keys: `plan` = one row per routine, `batches`, `files`).

Scope: 448 routine files, 491 routines (top-level labels), 32490 code lines, 2950 comments (density 0.09/line). Twin found for 404 routines (2657/29334 = 0.09 in 93S vs 4470/11383 = 0.39 in 93G). Twin lookup: name equality 367, case 5, bank-copy suffix 4, docs/unmatched rows 14, `92/93G <name>` note 1, parent_local 14; no twin 86.

Action rules: port = twin has density >1.25x and >=2 more comments (or twin has a label comment and 93S has none), line-count ratio 93S/93G within 0.5-2.5; adapt = twin better but code size differs, or no better twin but density <0.30 on >=6 lines; write = no twin and no label comment or density <0.35 on >=4 lines; ok = rest (and routines of <=2 lines with a label comment). Note: 65816 vs 68000 code always differs, so `port` means 'same structure, translate the comment to the new registers', never copy verbatim.

## Systematic issues

- Density: 93S has 0.09 comments per code line; 93G twins have 0.39. Only 69 of 448 files exceed 0.25; 196 are below 0.10.
- CONTRIBUTING 4 says every label, local ones too, has a comment: 2524 of 2952 local labels (85%) have none. Top-level labels all have a trailing comment (491/491), but 441 of them do not say who calls them, 39 are under 25 characters, and 313 mention neither registers nor callers nor results.
- Header: none of the 448 routine files starts with a header comment (every file begins at the label). CONTRIBUTING 4 requires one. Decide whether a short one-line file header (what/neighbours/notes) is wanted for each, or only for multi-routine files (22 files). The label-line comment currently plays that role.
- Layout (check_comments.py): the tree is clean on the last run (an earlier run flagged one >110-column line in src/data/frames93s.asm; the working tree was changing during this analysis, src/inc/snes_regs.asm vanished too). Routine files are clean. Remaining style defects are not covered by the script: continuation lines of label comments are sometimes mis-indented (e.g. CheckBump line 3 `;   call a goalie...` starts at 2 tabs instead of the label-comment column), and body comments use `; ` with a space while 93G uses `;` + text; follow check_comments (comment at column 36).
- Other games: 2 comment hits in 2 routine files for game names or `92/93G` outside the allowed `92 <name>` form (mostly `93G setplayercolors`-style notes); no hard-coded ROM addresses (0) and no IDA names (0) in routine files. Data and header files are the problem area, see below.
- 93G comments to strip when porting: 68000 register names (d0-d7, a0-a6), `(a2)+`, `MOVE`-level descriptions, Genesis names (VDP, Vctrl, Vdata, Z80, PSG, `.w` addresses `$FFFF....`), 92/93 revision notes `IF REV`, and `Rev A` remarks. Translate to 65816 (A/X/Y, direct page, `.b/.w/.l`) and the SNES names (PPU, vram, OAM, DMA).
- Do not shorten or reword existing 93S comments that come from 92 (CONTRIBUTING 4); the `port` workers add comments, they only replace a 93S comment when it is factually wrong.
- `docs/name_map.csv` marks 93G-sourced names (297 rows source 93G, 30 rows 92G); `92G` rows (30) have a 92 twin only, so their 93G twin may be absent: workers should check ~/nhlpa93genesis only if the name resolves, otherwise write from the code.
